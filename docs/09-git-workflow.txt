==============================================================================
0. CORE PRINCIPLE: BRANCHES DESCRIBE FEATURES, NOT DAYS
==============================================================================

You may finish the MVP in 5 days, 7 days, or longer without renaming branches.
Keep these permanent branches:

  main       -> stable release / judged submission
  develop    -> integration branch for accepted features

Create SHORT-LIVED branches as needed:

  feature/meta-ai-validation
  feature/video-ingestion
  feature/object-tracking
  feature/safety-rule-engine
  feature/evidence-dashboard
  feature/benchmark-demo

Other optional naming conventions:

  fix/sam-response-parsing
  fix/tracking-id-collisions
  docs/architecture-guide
  chore/github-actions

Do not create every feature branch in advance. Start each new feature from the
LATEST develop branch after previous work has merged. Each branch belongs to
this ONE repository; you do not need six separate repositories.

Recommended flow:

   feature/meta-ai-validation --------PR----\
   feature/video-ingestion ----------PR-----+--> develop --release PR--> main
   feature/object-tracking ----------PR-----+
   feature/safety-rule-engine -------PR-----+
   feature/evidence-dashboard -------PR-----+
   feature/benchmark-demo ----------PR-----/

A PR is still useful for a solo engineer: it creates reviewable changes,
provides a test checkpoint, and gives judges an understandable commit history.

==============================================================================
1. IMPORTANT: PRESERVE YOUR EXISTING REMOTE REPOSITORY
==============================================================================

If your GitHub repository already has a README, LICENSE, commits, or code:
CLONE IT FIRST. Copy the new starter FILES into that clone as working-tree
changes. Do not replace its .git directory or rewrite remote history.

Never run any of these to force an overwrite:

  git push --force
  rm -rf .git
  rsync --delete ...

The downloaded ZIP is source files, not a Git history replacement.

Hackathon rule: The participant guide specifies Oct 27–Nov 4, 2026 as the
building period. Any starter code generated on Oct 26 predates that window.
Confirm permitted reuse, identify pre-event scaffolding honestly, and only
present qualifying NEW work created during the official event period.

==============================================================================
2. CLONE EXISTING REMOTE AND CREATE DEVELOP ONCE
==============================================================================

If you created https://github.com/El-Moatasem/visionguard-ai already:

  mkdir -p ~/Projects
  cd ~/Projects
  git clone https://github.com/El-Moatasem/visionguard-ai.git
  cd visionguard-ai
  git status
  git branch -a
  git switch main
  git pull --ff-only origin main

Optional backup branch before replacing existing README/project files:

  git switch -c backup/pre-starter-import
  git push -u origin backup/pre-starter-import
  git switch main

Create the develop branch ONLY IF it does not already exist:

  git switch -c develop
  git push -u origin develop

If develop already exists remotely, use this instead:

  git fetch origin
  git switch --track origin/develop

If the repository has no commits at all, create an initial README commit first
and push it to main. If GitHub uses master rather than main, adapt the commands
or rename the default branch in GitHub settings.

==============================================================================
3. IMPORT STARTER FILES INTO THE FIRST FEATURE BRANCH
==============================================================================

Assume you downloaded and unzipped:

  ~/Downloads/VisionGuard_AI_Starter_Feature_Branches.zip

That ZIP extracts to:

  ~/Downloads/visionguard-ai/

Make the first feature branch in your existing CLONED repository:

  cd ~/Projects/visionguard-ai
  git switch develop
  git pull --ff-only origin develop
  git switch -c feature/meta-ai-validation

Copy source files INTO this clone. The command intentionally does NOT delete
files that are already in your remote clone:

  rsync -av \
    --exclude='.git/' \
    --exclude='.env' \
    --exclude='.venv/' \
    --exclude='__pycache__/' \
    --exclude='.pytest_cache/' \
    ~/Downloads/visionguard-ai/ ./

Review BEFORE staging:

  git status
  git diff --stat
  git diff -- README.md

Install and run local tests:

  python3 -m venv .venv
  source .venv/bin/activate
  python -m pip install -r requirements.txt
  python -m pytest backend/tests -q

Review staged changes and commit:

  git add -A
  git diff --cached --stat
  git commit -m 'feat(meta): add model API and SAM validation scaffold'
  git push -u origin feature/meta-ai-validation

Create a GitHub Pull Request:
  base    = develop
  compare = feature/meta-ai-validation

After reviewing tests/diff, merge the PR. Then sync locally:

  git switch develop
  git pull --ff-only origin develop

You MAY replace matching source files/README.md through a normal Git commit.
You should NOT overwrite the Git repository itself or rewrite its history.

4. REPEATABLE FEATURE WORKFLOW
==============================================================================

Always begin from the latest develop (change FEATURE_NAME to the real name):

  cd ~/Projects/visionguard-ai
  git switch develop
  git pull --ff-only origin develop
  git switch -c feature/FEATURE_NAME

Make the change, update documentation, test, and push:

  python -m pytest backend/tests -q
  git add -A
  git diff --cached --stat
  git commit -m 'feat: describe completed capability'
  git push -u origin feature/FEATURE_NAME

Create a PR:  feature/FEATURE_NAME -> develop

After merging the PR:

  git switch develop
  git pull --ff-only origin develop

If you continue working in the same branch after its first push:

  git add -A
  git commit -m 'fix: clarify the next fix'
  git push

If you need the latest integration changes WHILE on a feature branch:

  git fetch origin
  git merge origin/develop
  # resolve conflicts, run tests, git push (never force push)

==============================================================================
5. FEATURES AND SUGGESTED COMMIT MESSAGES
==============================================================================

A. feature/meta-ai-validation
   Purpose: Confirm usable Meta credentials; run Muse Spark ping; run SAM 3.1
   on one licensed short clip; save actual track IDs, boxes, and masks.
   Commit: feat(meta): validate Muse Spark and SAM video inference
   Completion: live SAM output inspected and limitations recorded.

B. feature/video-ingestion
   Purpose: FastAPI video upload/validation, local temporary storage,
   React/Next.js video playback, safe file constraints.
   Commit: feat(video): implement upload API and clip playback
   Completion: upload an MP4 and play it locally.

C. feature/object-tracking
   Purpose: Normalize SAM tracks, stable track identity in each clip,
   pedestrian/forklift overlays and timestamp synchronization.
   Commit: feat(tracking): add normalized object tracks and overlays
   Completion: tracked subjects can be seen on video across frames.

D. feature/safety-rule-engine
   Purpose: Muse Spark translates natural language to VALIDATED rule JSON;
   deterministic Python engine detects configured zone entry and duration.
   Commit: feat(rules): detect configured spatiotemporal safety events
   Completion: at least one positive and one negative example validated.

E. feature/evidence-dashboard
   Purpose: Incident timeline, seek-to-frame, track evidence, explanation,
   human review and exportable report.
   Commit: feat(evidence): add incident review dashboard and reports
   Completion: a reviewer can inspect why an event was flagged.

F. feature/benchmark-demo
   Purpose: Repeatable evaluation, no-alert/alert/ambiguous examples,
   visible model limitations, deployment notes and 3-minute demo script.
   Commit: test(demo): add evaluation fixtures and submission readiness
   Completion: all essential tests pass; a documented end-to-end demo works.

You may combine adjacent features into fewer PRs if that produces cleaner
changes. The goal is a convincing, reliable MVP, not six mandatory PRs.

7. RELEASE DEVELOP TO MAIN
==============================================================================

Once develop is stable:

  git switch develop
  git pull --ff-only origin develop
  python -m pytest backend/tests -q

Create a GitHub PR:
  base = main
  compare = develop
  title = release: VisionGuard AI hackathon MVP

Review and merge, then:

  git switch main
  git pull --ff-only origin main
  git tag -a v0.1.0-hackathon -m 'VisionGuard AI hackathon submission'
  git push origin v0.1.0-hackathon

Pre-submission checklist:
  [ ] main branch is public and has verified runnable code
  [ ] Meta calls are real (or demo materials clearly distinguish fixtures)
  [ ] secrets, private data and unlicensed videos are excluded
  [ ] documentation records exact newly-built contributions and dates
  [ ] local run and test commands match the released code
  [ ] positive, negative, and uncertain cases are shown accurately
  [ ] 3-minute demo link is viewable by judges
  [ ] required information is submitted before the deadline

Submission: https://cerebralvalley.ai/e/meta-ai-developer-hackathon/hackathon/submit
